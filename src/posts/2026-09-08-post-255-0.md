## Langkah 1: Sediakan Skrip Incremental Sync Data

Alright, Langkah 1, kita kena buat skrip Python yang boleh 'tangkap' dan sync perubahan data dari database kita. Macam CCTV, tapi untuk data!

**Ideanya Macam Ni:**

*   **Cari Tarikh 'Update':** Cara paling senang, setiap jadual dalam database anda patut ada satu kolum `updated_at`. Skrip kita akan catat bila kali terakhir dia sync. Lepas tu, setiap kali dia jalan, dia cuma ambil data yang `updated_at` dia lebih baru dari tarikh sync yang lepas. Bijak, kan?
*   **Change Data Capture (CDC):** Kalau sistem anda lagi canggih, boleh guna teknologi CDC. Ini akan pantau log transaksi database dan kesan semua jenis perubahan (data baru masuk, data lama diubah, data kena delete). Cara ni memang power, tapi memanglah kena setup lebih sikit.

**Aliran Skrip Kita (Secara Ringkas):**

1.  **Cari Masa Sync Terakhir:** Baca dari mana-mana fail log atau database anda sendiri untuk tahu bila last skrip ni jalan.
2.  **Connect ke Database:** Guna library Python macam `psycopg2` (untuk PostgreSQL) atau `mysql-connector-python` (untuk MySQL) untuk sambung.
3.  **Tarik Data Baru/Berubah:** Tulis query yang hanya akan ambil data yang `updated_at` dia lebih baru dari masa sync terakhir.
    ```python
    # Contoh ringkas guna Python
    last_sync_timestamp = get_last_sync_timestamp()
    new_data = db_connection.execute(
        f"SELECT * FROM products WHERE updated_at > '{last_sync_timestamp}'"
    )
    ```
4.  **Simpan Sementara:** Data yang dah tarik tu, simpan dulu kat tempat transit (staging area), mungkin dalam bentuk JSON atau CSV.
5.  **Update Masa Sync:** Lepas semua data dah berjaya diambil, jangan lupa update timestamp terakhir tu kepada masa sekarang atau masa rekod paling baru yang diambil.

Oh ya, pasal DeepSeek API Key tu, penting gila nak jaga. Pakai `dotenv` ke, apa ke, asalkan secure. Boleh tengok panduan ni untuk info lanjut pasal keselamatan API Key anda: [Cara Urus DeepSeek API Key dan Had Penggunaan](/posts/deepseek-api-key-and-limits/).

## Langkah 2: Konfigurasi Proses Index Rebuild

Dah dapat data baru, sekarang masa untuk Langkah 2: proses data tu dan update indeks vektor kita. Part ni yang buat data kita jadi 'faham' untuk AI. Prosesnya melibatkan tukar teks jadi 'embedding' (macam nombor-nombor unik yang mewakili makna teks) dan letak dalam vector store.

**Aliran Skripnya Macam Ni (Ringkas):**

1.  **Ambil Data Baru:** Baca balik data yang kita simpan sementara tadi dari Langkah 1.
2.  **Cuci & Sediakan Data:** Pastikan data tu bersih dan dalam format yang betul untuk proses embedding. Contohnya, gabungkan semua teks berkaitan jadi satu string panjang.
3.  **Hasilkan Embedding:** Guna model embedding yang kita setup kat Ollama (contohnya, `nomic-embed-text`) atau DeepSeek Embedding API. Ini akan tukar teks anda jadi vektor numerik.
    ```python
    # Contoh ringkas Python untuk embedding guna Ollama
    from ollama import Client
    client = Client(host='http://localhost:11434') # Make sure your Ollama server is running!

    embeddings_list = []
    for item in new_data:
        text_to_embed = item['product_name'] + " " + item['description']
        response = client.embeddings(model='nomic-embed-text', prompt=text_to_embed)
        embeddings_list.append(response['embedding'])
    ```
4.  **Update Vector Store:** Masukkan embedding baru ni ke dalam vector store anda. Sesetengah vector store boleh buat `upsert` (kalau ada update, dia update; kalau takde, dia tambah baru) yang memang cekap. Kalau tak support `upsert`, anda mungkin kena delete rekod lama dan masukkan yang baru. Ingat, kualiti prompt pun penting untuk hasil RAG yang power; boleh semak [asas prompt yang baik](/posts/deepseek-prompt-basics/) untuk tips.

## Langkah 3: Jadualkan Automasi Anda

Oke, dah ada skrip sync dan rebuild, sekarang kita buat dia jalan sendiri! Inilah Langkah 3, jadualkan skrip anda supaya dia automatik buat kerja. Kuranglah kerja manual, dan sistem anda sentiasa segar bugar.

**Untuk Geng Linux/macOS (guna `cron`):**

1.  Buka terminal, dan taip `crontab -e`.
2.  Tambah je baris ni kat hujung fail `crontab` anda:
    ```
    0 * * * * /usr/bin/python3 /path/to/your/sync_script.py >> /path/to/sync_log.log 2>&1
    0 * * * * /usr/bin/python3 /path/to/your/rebuild_script.py >> /path/to/rebuild_log.log 2>&1
    ```
    Kod di atas akan suruh skrip jalan setiap jam (pada minit ke-0 setiap jam). Boleh je adjust `0 * * * *` ikut kesesuaian anda (contohnya, `0 3 * * *` kalau nak dia jalan setiap hari pukul 3 pagi).

**Untuk Geng Windows (guna Task Scheduler):**

1.  Cari je 'Task Scheduler' kat Start Menu.
2.  Pilih "Create Basic Task" atau "Create Task" kalau nak kawalan lebih.
3.  Ikut je step by step yang dia bagi. Nanti anda akan set nama, description, bila nak trigger (contohnya, setiap hari atau setiap jam), dan apa action dia (iaitu, suruh `python.exe` jalankan skrip Python anda).

Penting sangat! Pastikan skrip sync tu jalan dulu, baru skrip rebuild. Boleh set masa berlainan atau gabungkan je dua-dua skrip tu jadi satu 'master script'.

## Tips Tambahan untuk Prestasi Terbaik

Akhir sekali, beberapa tips pro untuk make sure sistem anda memang 'terbang' laju dan stabil:

*   **Batching Data:** Kalau data anda banyak gila, jangan proses satu-satu. Buat dalam kelompok (batches) kecil. Lagi efisien dan tak membebankan sangat memori atau GPU server anda.
*   **Perhatikan Log:** Sentiasa check log skrip anda. Macam doktor check pesakit, untuk pastikan takde error atau masalah prestasi. Sistem yang stabil memang kena selalu dipantau. Kalau nak sistem anda lagi kebal, boleh tengok [Panduan DeepSeek API Retry](/posts/deepseek-api-retry-guide/) ni.
*   **Handle Error:** Masukkan `try-except` dalam skrip anda. Kalau ada masalah kecil, skrip tak terus 'crash'.
*   **Query Database yang Laju:** Pastikan query untuk incremental sync tu dioptimumkan. Guna indeks pada kolum `updated_at` untuk prestasi yang super pantas.
*   **Eksperimen Kekerapan:** Mula dengan sync yang tak terlalu kerap (contohnya, setiap beberapa jam). Kalau data anda asyik berubah, dan kesegaran data tu kritikal, barulah tingkatkan kekerapan. Tak perlu lah sync setiap 5 minit kalau data berubah sekali seminggu.

## Soalan Lazim (FAQ)

Ini dia soalan-soalan yang selalu orang tanya:

**S1: Apa benda RAG ni dan kenapa saya perlu pakaikan dia?**

RAG (Retrieval-Augmented Generation) ni satu teknik AI yang bagi 'kuasa tambahan' kat model bahasa besar (LLM) macam DeepSeek. Dia boleh pergi cari maklumat dari luar (database anda!) sebelum bagi jawapan. Anda perlukan dia kalau nak chatbot atau sistem AI anda bagi jawapan yang tepat, ikut data bisnes anda sendiri, dan nak elak LLM merepek atau 'halusinasi' yang selalu terjadi kat LLM biasa.

**S2: Kena ke saya rebuild indeks tu setiap kali ada data baru?**

Tak payah lah selalu. Kalau ada perubahan kecil atau data baru masuk, cukup je buat 'incremental update' atau 'upsert' (update kalau dah ada, masukkan baru kalau takde) kat vector store anda. Rebuild semua tu biasanya kalau ada perubahan besar pada struktur data atau nak buat pengoptimuman. Kalau tak, buang masa je!

**S3: Database jenis apa yang boleh saya guna untuk setup ni?**

Hampir semua database moden boleh jalan, tak kira SQL (macam MySQL, PostgreSQL) atau NoSQL (MongoDB). Kuncinya adalah, database tu kena boleh kesan perubahan data. Boleh guna kolum `updated_at`, trigger database, atau teknologi Change Data Capture (CDC) logs.

**S4: Kalau data saya dah macam gunung, nanti perlahan tak?**

Untuk data yang melambak-lambak, ada cara nak lajukan proses ni. Pertama, proses embedding dalam 'batches' (kelompok kecil). Kedua, kalau pakai Ollama local, pertimbangkan guna server dengan GPU yang power untuk proses embedding yang lagi laju. Ketiga, pastikan vector store anda pun dioptimumkan untuk operasi skala besar.

**S5: Apa beza sync incremental dengan sync penuh?**

Sync incremental ni ibarat anda cuma kemas rumah yang kotor sikit je, bukan kemas satu rumah dari A sampai Z. Dia cuma proses data yang berubah sejak kali terakhir sync. Ini memang jimat masa dan sumber. Sync penuh pula, dia akan proses *semua* data setiap kali, tak kira ada perubahan ke tak. Sesuai untuk database yang sangat kecil, atau masa mula-mula setup je.
